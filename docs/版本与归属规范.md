# 版本与归属规范

> 类型:流程规范。
> 性质:现行文档。
> 归属:`文档自身`（同时约束全部服务与文档）。
> 适用版本:平台 `4.0.0+`。

本文是 AAgent 版本号与文档归属的**唯一可执行规则来源**。任何"这个该不该升版本""这篇文档归谁管"的问题，以本文为准。编号体系（为什么不用 SemVer、三个数字各是什么）的原理见 [版本控制](版本控制.md)。

---

## 0. 要解决的问题

引入本文之前的状态（基线事实）：

- 仓库 154 个提交（2026-07-30 起），只有两个手工标签：`v2`（**附注标签**，message `stable v2`，即 `v2.x.y-beta`）与 `v3`（**轻量标签**，无 message，即 `v3.x.y-beta`），都不含 PATCH、无法排序，也不表示"哪一组改动被冻结过"。另有两次只在**提交信息**里自封的版本（`chore: release v1.0.0` 即 `v1.x.y-alpha`、`stable v1` 即 `v1.x.y-beta`），根本没打标签；它们都是本项目自有三代编号的早期雏形，本项目**从未正式采用过 SemVer**，直到 `4.0.0` 才第一次把它系统化。
- 没有 `CHANGELOG`，没有代码可读的版本号，"线上跑的到底是哪份代码"无法回答。
- 文档只有 `docs/审查日志/` 与 `docs/日志/` 有 `> 类型/性质` 元信息头，`docs/17..26` 主题设计文档、`docs/webUI/`、`docs/功能全景/`、`docs/论文survey/` 全都裸奔，读者无法判断一篇文档是否过期、由哪部分代码负责维护。
- 提交信息粒度随意（`文档整理`、`模型配置bug`、`map-content(待复核)`），无法据此还原"某一版包含什么"。

结论：需要**三层版本号**（平台 / 协议 / 服务）回答"是什么版本"，需要**标签 + CHANGELOG**回答"这一版包含什么"，需要**文档归属元信息**回答"这篇归谁管、还准不准"。

## 1. 三层版本号各管什么

| 层 | 管什么 | 编号格式 | 载体 | 变更频率 |
|---|---|---|---|---|
| **平台版本** | 整个 AAgent 平台 | `MAJOR.MINOR.PATCH`（`MAJOR`=架构/引擎代数） | `version.json` 的 `platform` + git tag + `CHANGELOG.md` | 引擎换代 → MAJOR；新功能 → MINOR；修 bug/改文档 → PATCH |
| **协议版本** | 服务之间的数据契约：`event`（队列事件信封）、`workflow`（Workflow JSON） | `MAJOR.MINOR` | `version.json` 的 `protocol` + 对应设计文档元信息头 | 只在契约变化时 |
| **服务版本** | 单个服务上次参与迭代的平台版本 | `MAJOR.MINOR.PATCH` | `version.json` 的 `services` + 各服务目录的 `version.json`（服务级副本） | 参与改动时同步为当次平台版本，否则停在旧值 |

三层彼此独立：平台升到 `v4.3.8` 时，`event` 协议可能仍是 `1.3`；没参与这次改动的服务停在它上回参与时的版本。

**三层都不做兼容层。** 本仓库只有一个使用者，破坏性变更直接改、直接升版本（通常落在 MINOR，见 §2），不写迁移分支、不写"友好报错"照顾旧数据；也不对任何历史数据（含数据库内的历史数据）做兼容。

## 2. 平台版本规则（`MAJOR.MINOR.PATCH`）

编号**不是 SemVer**：它不表达兼容性承诺，只表达"第几代引擎、第几个功能、第几次修补"。git 标签写 `vMAJOR.MINOR.PATCH`。

- **MAJOR —— 架构 / 引擎代数**：引擎换代（调度模型、执行范式的整体替换）时 +1，同时把 MINOR、PATCH 清零。
- **MINOR —— 功能代数**：每做完一个功能 +1，同时把 PATCH 清零。
- **PATCH —— 修补代数**：修 bug / 改文档，每改一次 +1 并 commit。
- `platform` 的定义就是**最新一版**：`version.json.platform` 始终等于仓库当前所处的平台版本。

### 2.1 当前在哪一代

当前 `MAJOR = 4`——引擎是第四代（**分 task 同步 FIFO 调度**）。前几代不回溯补号，历史以 `CHANGELOG.md` 的「主线回填」为准。

### 2.2 什么改动触发什么级别

判定看改动性质，不看改动行数：

| 改动性质 | 例子 | 版本动作 |
|---|---|---|
| 引擎 / 架构换代 | 执行范式整体替换 | MAJOR |
| 新增功能（含节点类型增删、端口/API/契约变化） | 新增 `map_content_get`；`/api/tools` → `/api/tools/local` | MINOR |
| 修 bug | 修 `workflow_validator` 的 KeyError | PATCH |
| 改文档 | 修订设计文档正文或元信息头 | PATCH |
| 重构 / 注释 / 测试（行为等价、文档不动） | — | **不动版本号** |

破坏性变更**不特殊对待**：本仓库不承诺兼容，改了就按上表归类。

### 2.3 发布节奏

- **一次发布 = 一次打标签**，版本号在发布时确定。**不允许在每个提交里改版本号**——这是"一锅粥"最常见的来源。
- 每个标签指向的提交必须是**可运行状态**，且容器内测试全绿（`agent` / `tool_server` / `manager_webui` 三处 `python -m unittest discover -p "test_*.py"`）。
- 无外部可见变化的内部改动（重构、测试、格式）不单独发布，累积进下一个 MINOR 或 PATCH。
- 不急：没有值得记住的改动就不打标签。宁可 10 个提交一个版本，也不要一个提交一个版本。

## 3. 协议版本规则

`event` 与 `workflow` 是**两条独立版本线**，格式 `MAJOR.MINOR`。**不加 PATCH**：对历史数据（含数据库内的历史数据）一律不做兼容，"变没变"就是全部信息。

- **MAJOR —— 协议大版本**：协议整体换代（信封结构 / 契约重写）时 +1，同时清零 MINOR。
- **MINOR —— 协议版本**：协议面每变化一次 +1——字段增删改名、语义反转、队列方向变化、新增 `event_type`、新增端口类型，全部算 MINOR。
- 留两个数只是用着束缚，没有实际意义。

- **记录位置**：`version.json` 的 `protocol` 字段；对应设计文档（`docs/20-Event协议与流转.md` 等）的元信息头写 `> 协议版本:event 1.0`。
- **协议版本与平台版本的对应关系必须写进 CHANGELOG**：每个平台版本条目里注明它携带的协议版本，否则无法回答"哪个平台版本能跟哪个服务版本通信"。
- 协议变化时全部生产者与消费者**同批更新**，不留兼容分支。
- 阶段二（尚未落地，见 §10）：Event 信封与 Workflow JSON 顶层增加 `schema_version` 字段，并在消费边界校验；不匹配时直接拒绝，不做兼容。

## 4. 服务版本规则

服务共 8 个：`agent`、`webui_py`、`manager_webui`、`workflow_editor`、`tool_server`、`tool_provider`、`qqbot`、`qqbot_consumer`。

- **服务版本不是独立版本序列**，它只表示"该服务上一次参与迭代时的平台版本"。
- **参与改动时同步为平台版本**：平台从 `v4.3.7` 更新到 `v4.3.8`，这一版参与改动的服务全部记为 `v4.3.8`；没参与的服务停在旧值。
- **默认等于平台版本。** `version.json` 的 `services` 里可以不列某个服务，表示"跟随 `platform`"。
- **只有单独发布时才写独立值**：例如把 `tool_server` 单独回滚到旧版本、或单独部署到还在跑旧平台版本的环境。此时在 `version.json.services` 里显式写出该服务的版本号。
- **不可能超前于平台版本**：`platform` 的定义就是最新版本，服务版本只能等于或落后于它。
- **服务版本不用于判断兼容性**：服务间能否通信只看 `protocol`；而且协议一致也不代表整体业务能跑通。
- 服务版本的服务内可见性：每个服务目录有 `version.json`（服务级清单副本，§5），HTTP 服务在 `/api/version` 暴露（阶段二）。

## 5. 版本号的唯一来源与同步

### 5.1 事实约束

`docker-compose.yml` 里每个服务的构建上下文是**它自己的目录**（`build: ./agent`），`Dockerfile` 用 `COPY . .` 拷到 `/app`。因此**仓库根的文件不会进入任何镜像**。版本载体必须落在服务目录内。

### 5.2 规则

1. **`version.json`（仓库根）是权威清单**，结构固定：

   ```json
   {
     "platform": "4.0.0",
     "protocol": { "event": "1.0", "workflow": "1.0" },
     "services": {}
   }
   ```

   `services` 为空对象 = 全部服务跟随 `platform`。

2. **每个服务目录一个 `version.json`**，是该服务那一版的**服务级清单副本**——根清单去掉 `services`：

   ```json
   {
     "platform": "4.0.0",
     "protocol": { "event": "1.0", "workflow": "1.0" }
   }
   ```

   它随镜像进容器，供 `/api/version` 等运行时代码直接读取。`platform` 必须等于根清单为该服务解析出的版本；与该版本同步的服务其 `protocol` 必须等于根协议，单独落后于平台的服务携带自己那一代的协议、只要求格式合法。

> 不采用"从根 `version.json` 生成服务 `version.json`"的方式：那会引入构建步骤，而当前构建链（`docker compose build`）没有生成阶段。

## 6. 标签规范

- 格式：`v<MAJOR>.<MINOR>.<PATCH>`。
- 类型：**annotated tag**（`git tag -a`），不用轻量标签。
- message：第一行 `v4.3.8 — <一句话概括>`。
- 只在 `main` 上打标签，且该提交测试全绿。
- **现存 `v2` / `v3` 保留不删**：它们是仓库里唯一的旧锚点，删除会让 2026-08-02 ~ 08-22 之间的历史失去可读落点。它们是本套编号的早期雏形（`v2.x.y-beta` / `v3.x.y-beta`），但无载体，不构成正式版本，统一登记在 §6.1。
- 新标签一律用 `v` + 三段式，**不带任何后缀**（`-alpha` / `-beta` 之类的后缀今后不再使用）；`v2` / `v3` 这类不含 PATCH 的旧编号也不再使用。
- **历史回填不改写历史**：旧提交不补标签、不 `rebase`、不 `amend`。历史内容以归纳文字写进 `CHANGELOG.md`，并登记为下表锚点。

### 6.1 历史锚点登记表

版本体系引入（`v4.0.0`）之前的历史不自造版本号，但保留全部可追溯的锚点。它们是本套 `vMAJOR.MINOR.PATCH` 编号的早期雏形，`-alpha` / `-beta` 后缀只是表意，**今后不再使用后缀**：

| 锚点 | 形态 | 指向提交 | 日期 | 说明 |
|---|---|---|---|---|
| `chore: release v1.0.0` | 仅提交信息 | `d246dc6` | 2026-08-01 | `v1.x.y-alpha`；只有提交信息、**没打标签**，不构成版本 |
| `stable v1` | 仅提交信息 | `f0ef10c` | 2026-08-01 | `v1.x.y-beta`；同上 |
| `v2` | **附注标签**（tag 对象 `60ab1a7`） | `f39e242` | 2026-08-02 | `v2.x.y-beta`；标签 message 为 `stable v2`；指向的是 `prepare for v2` 那次提交 |
| `v3` | **轻量标签**（无 tag 对象） | `bcce929` | 2026-08-22 | `v3.x.y-beta`；标签名 `v3`，无 message |

用法：`git show v2` / `git log v3 --oneline -5`。这些锚点**不表示任何兼容性承诺**，只是"当时停在这里"的痕迹。

## 7. CHANGELOG 规范

- 位置：仓库根 `CHANGELOG.md`。
- 格式：[Keep a Changelog 1.1.0](https://keepachangelog.com/zh-CN/1.1.0/)，中文条目，版本**倒序**（新的在上）。
- 固定分类：`新增` / `变更` / `修复` / `移除` / `破坏性变更` / `协议版本`。空分类不写标题。
- 顶部保留 `## [Unreleased]` 段，记录尚未发布但值得记住的改动；发布时把内容移到新版本标题下。
- **每个已发布版本必须写 `协议版本` 段**，注明该版本携带的 `event` / `workflow` 协议版本（不变也写明"沿用 x.y"）。
- 只记"值得记住的"改动：能回答"这一版跟上一版有什么不同"。内部重构、格式调整不进 CHANGELOG。
- 不单独维护"修复记录"章节：git 历史 + `docs/日志/` 是实现层记录，CHANGELOG 是发布层记录。

## 8. 文档归属元信息规范

### 8.1 元信息头格式

紧跟在 H1 标题之后，四个通用字段**全部必填**（协议类文档另加第五字段 `协议版本`），用引用块书写：

```markdown
> 类型:设计文档。
> 性质:现行文档。
> 归属:`agent/`。
> 适用版本:平台 `4.0.0+`。
```

#### 字段取值

**`类型`**（文档体裁，可组合）：

| 取值 | 用于 |
|---|---|
| `设计文档` | `17..26` 系列主题设计 |
| `目录说明` | 各目录的 `README.md` |
| `索引清单` | 只登记"有什么文件在哪" |
| `汇总清单` | 当前问题清单 |
| `审查报告` / `审计报告` | 某次审查的产出 |
| `核验记录` | 逐条判定与证据 |
| `实现记录` / `修复记录` | `docs/日志/` 下的过程记录 |
| `流程规范` | 本文、`docs/审计.md` |
| `调研笔记` | `docs/论文survey/` |
| `一次性产出` | 交叉验证一类不做维护的报告 |

**`性质`**（生命周期，决定"还能不能信"）：

| 取值 | 含义 |
|---|---|
| `现行文档` | 描述当前行为，与源码冲突时以**源码**为准 |
| `历史快照` | 冻结在某次变更前后，**只用于追溯**，行号与链接已作废 |
| `已作废` | 明确失效，可删除但暂留作对照 |

**`归属`**（谁负责在代码变更时同步这篇文档）——这是本规范对"文档归属分不清"的正面回答：**归属 = 该文档声称描述的那部分代码**。取值为代码责任域，多值用 ` + ` 连接：

| 取值 | 覆盖范围 |
|---|---|
| `agent/` | 执行器、节点契约、校验器、队列消费 |
| `webui_py/` | :8081 事件流 / 终端 / 事件绑定 |
| `workflow_editor/` | :8082 画布编辑器 |
| `tool_server/` | :8083 工具注册、任务、控制台 |
| `tool_provider/` | 工具实际执行方 |
| `manager_webui/` | :8084 Workflow / 文档 / 模型 / Session |
| `qqbot/` + `qqbot_consumer/` | QQ 事件源与适配 |
| `基础设施` | compose、Dockerfile、`.env.example` |
| `跨服务` | 同时约束两个以上服务（Event 协议、节点契约并列） |
| `文档自身` | 规范、索引、目录说明 |

**`适用版本`**（这篇文档对应哪个平台版本）：现行文档写 `平台 0.x.y+`；历史快照写 `—`。

**`协议版本`**（第五字段，**仅协议类文档必填**）：定义协议的设计文档额外写一行，如 `> 协议版本:event 1.0。`。适用于 `docs/20-Event协议与流转.md`（`event`）与 Workflow JSON 契约文档（`workflow`）。普通服务设计文档不写此行。

### 8.2 维护规则

1. **新建文档必须带四字段。** 缺字段的文档在 `docs/README.md` 索引里标为"待补"，视同未完成。
2. **性质只降不升**：`现行文档` 可以改为 `历史快照` 或 `已作废`，反向不允许（要"复活"就重写一篇）。
3. **归属触发同步义务**：改动了某个服务的契约面代码，必须检查所有 `归属` 含该服务的文档是否需要同步。这是归属字段的**唯一实际用途**——不是分类美观，而是变更时能反查出该更新哪些文档。
4. **改动文档内容时同步更新元信息头**：尤其是 `适用版本`，文档跟进到新版本后要跟着走。
5. **归档**：文档转为历史快照时移入该目录下的 `归档/` 子目录，正文只做机械调整（加归档说明、修相对链接），不回写结论。
6. **冲突判定**：`性质` 为 `现行文档` 且与源码冲突时，以源码为准，并把文档改为 `历史快照` 或修正。

| `docs/20-Event协议与流转.md` | 设计文档 | 跨服务 | Event 协议正文，需带 `协议版本` |

| `docs/版本与归属规范.md` | 流程规范 | 文档自身 | 本文 |

### 8.4 命名规则
