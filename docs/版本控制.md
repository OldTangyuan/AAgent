# 一套全新的适用于分布式系统的version

> 类型:流程规范。
> 性质:现行文档。
> 归属:文档自身。
> 适用版本:平台 `4.0.0+`。

落地规则（载体、校验、标签、文档归属）见 [版本与归属规范](版本与归属规范.md)。

## 目的
我的文档经常会过期,迭代太快又懒得改bug,甚至有时候bug被架构重构没了文档还在,这套version的意义在于便于与文档对齐;同时满足github打tag复盘的需求

## 为什么不用semVer
根据我的理解,semVer主要用于一个明确的商业品上,比如jetbrain的产品,立项之初就确定好了技术方案(不然养架构师吃白饭?),且需求十分明确(国内产品经理的朝令夕改算什么?),所以只需要考虑api兼容性,不存在需求/架构完全推翻的情况。但这个项目作为一个大型系统、探索性制品,必然是会随着外界变化不断翻版的,semVer的MAJOR就必须锁定在0,浪费了一位。同时,这是一个分布式系统,每个service相对灵活,强行统一version也没意义,当然,给每个service一个version好像确实也没用,唯一用处是提醒我protocol不兼容了要重新build。

## 字段定义
### platform version
format : vMAJOR.MINOR.PATCH  

- MAJOR : 架构/引擎 代数,更新后MINOR与PATCH清零
- MINOR : 功能 代数,每新做一个功能就+1,PATCH清零
- PATCH : 修bug/改文档,修改后+1,并commit

举例:
当前引擎为第四版,分task同步FIFO调度 MAJOR:4  
当前功能是修订版本控制协议,第一个功能 MINOR:0
当前正在修订第一批文档 PATCH:0
platform version : v4.0.0

platform version的定义就是最新的version

### protocol version
format : vMAJOR.MINOR

MAJOR ：协议大版本,更新后清零MINOR
MINOR : 协议版本,每次加一

不再增加PATCH,因为数据格式的兼容会对代码带来很大负担,这个项目默认不对任何历史数据进行兼容,包括数据库中的历史数据
为什么要两个数?just用着束缚,没实际意义

### service version
与platform version一样,但可以落后于platform version 但具体能否与别的service兼容取决于protocol version是否一致(不可能超前于platform version,因为platform version的定义就是最新的version)  

注意:service version并不用于判断服务间兼容性,因为protocol version已经足够了;另外,更重要的一点是,分布式系统中兼容不代表整体业务可以正常运行。

注意,(正在改的一个或多个)service,先将platform version更新,再把service version同步为platform version。服务版本不是独立的版本序列，只是表示前一次参与迭代的平台版本。
举例:平台从 v4.3.7 更新到 v4.3.8 时，参与这次改动的服务全部记为 v4.3.8。

#### 为什么这么设计:
github上的MINOR就是最新MINOR,你难道指望我写一个服务还要把别的服务一起改掉吗?实际上通常情况是你半个月全在做某个service别的一动不动。
而且这个差异可以提醒你,某个service你已经多久没动过了。
最重要的是,这是在不拆分github repo的前提下,唯一可以标清楚tag的方式。
其实说,如果你要联合调试,那所有的service的version都会+1,它本身只是一个锦上添花的东西
