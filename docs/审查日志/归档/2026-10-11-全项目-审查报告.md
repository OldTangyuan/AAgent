## 2. 生产代码缺陷（只登记，未修改）

### A1 [高] agent 契约漏注册 `map_content_get`，含该节点的工作流无法执行

- 位置：`agent/workflow_contract.py` 的 `NODE_ARGUMENT_FIELDS_BY_TYPE`（缺 `"map_content_get": set()`）；`SUPPORTED_NODE_TYPES` 与 `data_ports_for_node` / `is_valid_connection` 都已包含该类型。
- 影响：`validate_workflow` → `_validate_node`（`agent/workflow_validator.py:178`）对任何 `map_content_get` 节点抛 `KeyError`（不是 `WorkflowValidationError`），worker 兜底打印“agent处理失败”，任务静默失败。
- 为什么能漏过：manager（`manager_webui/workflows.py`）与编辑器（`domain/serialization.js`）各自的同名字典都有该项，保存与导入全部放行；只有 agent 侧缺失。map-content 执行层测试直接调用节点函数、绕过了 `validate_workflow`，因此此前未暴露。
- 复现：`docker exec agent_aagent python -m unittest test_workflow_node.CallableWorkflowNodeTest.test_validator_and_parser_accept_map_content_nodes`。
- 建议修复（1 行）：在 agent 的 `NODE_ARGUMENT_FIELDS_BY_TYPE` 补 `"map_content_get": set(),`（本轮已用对账脚本验证：agent/manager/编辑器 4 处集合 + Inspector 模板共 24 类节点完全一致，补上后即全绿）。

### A2 [中] async 回调 `on` 含非字符串元素时校验器崩溃（TypeError）

- 位置（两份同构代码）：`agent/workflow_validator.py:389` 与 `manager_webui/workflows.py::tool_node_error`。
- 触发：`on: [{"status": "completed"}]` 之类的手工 JSON。`status not in {...}`（成员测试）与 `len(set(on))`（去重）对 dict/list 抛 `TypeError: unhashable`：agent 端表现为 worker 兜底异常，manager 端表现为 HTTP 500。
- 期望：这是坏数据，应返回 `WorkflowValidationError` / 400。
- 建议修复：在这两项检查前插入 `not all(isinstance(status, str) for status in callback["on"])`（利用 `or` 链短路，先判类型再判值）。

### A3 [中] tool_server：provider 输出不符合 `outputSchema` 时会打断 WebSocket 连接

- 位置：`tool_server/main.py` `handle_provider_event` 的 `Draft202012Validator(tool.outputSchema).validate(event.output)`。
- 已取证：本环境 `jsonschema 4.25.1` 中 `ValidationError` **不是** `ValueError` 子类（`SchemaError` 同样不是），而 `provider_socket` 的 `except (PydanticValidationError, SchemaError, ValueError)` 不包含它 → 异常穿透 `finally`（连接被注销）并终止该 provider 的 socket。
- 影响：provider 掉线；任务停在 `working` 直到 TTL；同步调用方等到自己的超时才拿到 202。合法行为应是「任务转 `failed`/记日志」，不应牵连连接。
- 建议修复：把输出校验包进局部 `try`，把 `jsonschema.ValidationError` 映射为 `{"status": "failed", "error": ...}` 的终态转移（或至少捕获后仅拒绝该次结果）。

### A4 [低] tool_server：`call_tool` 派发前 `next(...)` 存在竞态

- 位置：`tool_server/main.py`：先 `registry.get_tool(name)` 判存在，再 `tools = await registry.list_tools()` + `next(item["provider_id"] for item in tools if item["name"] == tool_name)`。
- 两次加锁之间 provider 掉线 → `StopIteration` → 500（应为 503 或回退到未派发分支）。
- 建议修复：`next(..., None)`，为 `None` 时按“provider 不可用”处理。

## 3. 接口对齐与边界问题（非直接崩溃，按优先级排列）

1. **双校验器分叉（长期项）**：manager 的 `node_format_error` 仍只覆盖 agent `validate_workflow` 的子集——缺 `router`/`construct_message`/`construct_content`/`construct_list`/`foreach`/`llm` 等类型的参数校验，也缺 workflow 节点 `workflowPorts` 形状校验。手工 JSON 可落库、运行时才发难；A1 是本类问题的一个实例（集合本身不一致）。
2. **保存时静默改数据**：`manager_webui/workflows.py::update_workflow` 仍用 `synchronize_metadata_ports` + `filter_invalid_connections` 静默丢弃“类型对不上”的连接（历史遗留 F 项）；编辑器导出→上传链路在“契约快照过期”时表现为 400（这条 OK），但手工调用 API 会无提示丢连接。
3. **`event_catalog` 与 producer 不一致**：`manager_webui/event_catalog.py` 的 `async_result` schema 写 `status: enum["completed","failed"]`，但 `tool_server` 的 `callback_event` 在 `on` 含 `working` 时确实推送 `status:"working"`。作为展示目录应补 `working` 或明确注明。
4. **重命名/删除的引用面**：`rename_workflow` 级联更新 `workflow_nodes` 快照与调用节点 `workflow_name`，但**不更新** webui_py 管理的 `event_bindings.workflow_name` 快照（绑定页展示会过期）；`delete_workflow` 不清理 binding，之后该事件类型每次进来都会产出 `error` 事件（行为可解释，但需知情）。
5. **入口 payload 不做端口类型强校验**：`task_worker` 按端口名直接把 `payload` 值写进数据槽（如 qq 的 `user_id` 是 int，端口是 `content`），类型问题延后到下游（如 LLM 的 “invalid message”）才爆，报错点远离源头。（更正：`workflow_id` **不是**意外覆盖——`test_task_worker.py` 明确断言“payload.workflow_id 会被绑定值覆盖，且当存在同名输入端口时把 workflow_id 暴露给该端口”，属有意设计。）
6. **LLM 空值语义不一致（已知未修）**：模型只回 `tool_calls` 时 `output=None` 会被下游视为“未到达”（`read_workflow_input` 的 `is not None` 判定），而 `reasoning` 用 `""`（视为已到达）。同节点的两类输出对空值语义不一致，建议统一。
7. **env 矩阵缺口**：`TOOL_CLIENT_DEFAULT_ASYNC_TIMEOUT_MS`（agent 实际读取，默认 600000）不在 `.env.example`；`TOOL_PROVIDER_REVISION` 三处默认不一致（example=2 / compose=5 / 代码=3）；`MONGO_EVENT_BINDING_COLLECTION`、`WORKFLOW_CONTEXT_*`、`WORKFLOW_SESSION_MAX_VALUE_BYTES`、`BILIBILI_DOWNLOAD_DIR` 未入示例；`ASR_URL`、`MODEL_ID`、`DEEPSEEK_MODEL` 已是死配置（无读取方）。
8. **sessions 列表查询索引**：`manager_webui/sessions.py` 用 `(updated_at,_id)` 排序 + `$or` 分页，但只建了 `updated_at` 单列索引（`session_updated_at`），数据量大时效率一般（低优先）。
9. **模型 API 明文回传 `api_key`**：本地单用户可接受（前端编辑回填依赖它，PUT 全量覆盖不会清空 key）；如未来打通外网需改为脱敏。
