## 这个目录为什么被重整过

重整之前,`审查日志/` 根目录堆着 6 份审查/审计报告、4 份活文档,`历史/` 下另有 15 份归档件,彼此编号体系不同(A1 / A-01 / F-02 / R1 指同一件事),而且全部写于一次大重构之前 —— 那次重构删掉了整条旧事件驱动链(`active` / `tool_excute` / `rpc_apply` / `rpc_review` / `tool_return`)、设置与 System Prompt 链路、`agent/command.py`、`agent/prompt/`,把 `webui_py` 的路由整体迁出,并新增了 `manager_webui` / `tool_server` / `tool_provider`。

结果是:历史日志里 **221 条问题有 44 条指向的东西已经不存在、10 条形态已变**;同时根目录的旧清单只覆盖"当初的五个服务",完全没有新服务。为了知道"哪些问题还真实存在",做了一次全量核验,然后:

1. 把**仍成立**的问题收进[汇总报告](汇总报告.md)(连续编号 1–52);
2. 把**逐条判定与证据**留在[核验报告](核验报告.md);
3. 把**全部历史快照与旧汇总**整体移入[归档/](归档/)(29 份),原位置的副本已删除,`历史/` 目录已并入 `归档/` 后删除;
4. 作废旧的"新报告先放根目录、等汇总吸收后再归档"流程 —— 它以产出速度超过了合并速度,是这个目录堆积的直接原因。

## 维护方式

- 只维护两份文档:**[汇总报告](汇总报告.md)**(问题清单)与**[核验报告](核验报告.md)**(判定与证据);
- 修掉一条问题,直接从汇总报告删掉该行(或在原行加删除线并注明"已修复",以便与历史报告编号对照);不再需要单独的"已修复"章节 —— git 历史就是修复记录;
- 新的审查/审计产出不再单独留存快照文件:结论直接并入汇总报告,证据并入核验报告;
- 实现/修复过程记录继续放 `../日志/`;
- 文档与源码冲突时,以源码为准。

## 归档说明

- [归档/](归档/) 内文件的**正文原样保留**,只做过三处机械调整:开头元信息加注"历史快照(已归档)"并指向汇总报告与核验报告、相对链接按新目录深度修正(例如 `历史/x` → `x`、`../日志/` → `../../日志/`、`../00-设计哲学.md` → `../../废弃旧文档/00-设计哲学.md`)、结尾多余空行归一;

- 归档里少数相对链接仍指向已删除的路径(例如指向 `历史/` 的旧链接),这是历史快照的正常状态,不做回写;
- `docs/废弃旧文档/` 存放的是**旧设计文档**(00-16),与这里的**旧审查记录**是两回事,不要混用。
